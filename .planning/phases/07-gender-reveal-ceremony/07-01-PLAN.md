    2. **Create service** at `server/src/services/genderReveal.ts`:
    This is the critical security layer. Import db directly for transactions.

    Functions:

    - `getRevealState(envelopeId: string, participantId: string)`: Returns `GenderRevealStateResponse`.
      - Get config from DB. If null, return `{ configured: false, keysValidated: 0, myKeyValidated: false, revealed: false }`.
      - Count validated keys (keyAValidated + keyBValidated as number).
      - If revealedAt is set, return with `revealed: true` and `gender: config.genderValue`.
      - Otherwise return `configured: true`, keysValidated count, `revealed: false`, NO gender.
      - Include `keyLength` from the length of keyA (both keys should be same length).
      - For `myKeyValidated`: the service doesn't track WHICH participant entered which key (per research recommendation — either key from either participant). So set myKeyValidated based on whether keysValidated > 0 AND this is a heuristic. Actually, simplify: since we accept any key from anyone, we can't track per-participant state. Set `myKeyValidated` to false always, and let the client track locally whether they've submitted. OR: track a `validatedByParticipantIds` approach. SIMPLEST: Since the research says "Accept either key from either participant," and we track keyA/keyB validated booleans but not WHO entered them, `myKeyValidated` should be returned as `false` unless we add tracking. Instead, omit `myKeyValidated` — no, the type requires it. SOLUTION: After a successful validation, the HTTP response tells the caller their key was accepted. The GET state endpoint returns keysValidated count. The client can track locally that it already submitted. Set `myKeyValidated: false` in the GET endpoint (it's a GET, not a personalized check). The client's local state from the POST response is the source of truth for whether THIS user already submitted.

    - `validateKey(envelopeId: string, participantId: string, key: string)`: Returns `ValidateKeyResponse`.
      CRITICAL: Use `db.$transaction` with `{ isolationLevel: 'Serializable' }`.
      - Get config within transaction. If null, throw 'REVEAL_NOT_CONFIGURED'.
      - If already revealed (keyAValidated && keyBValidated), return `{ status: 'already_revealed', gender: config.genderValue }`.
      - Check which key matches using constant-time-ish comparison (or just string equality — the threat model is DevTools, not cryptographic attacks, per research):
        - If key === config.keyA && !config.keyAValidated: set keyAValidated = true
        - If key === config.keyB && !config.keyBValidated: set keyBValidated = true
        - If key matches but already validated: return `{ status: 'key_already_used' }`
        - If neither matches: return `{ status: 'invalid_key' }`
      - Update the config row (set validated flag, and if BOTH now validated, set revealedAt = new Date()).
      - If both validated after update: return `{ status: 'revealed', gender: config.genderValue }`.
      - Otherwise return `{ status: 'waiting_for_partner', keysValidated: 1 }`.

    - `configureReveal(envelopeId: string, data: ConfigureGenderRevealRequest)`: Admin creates or updates config. Check if config exists. If yes, update (but only if not already revealed — don't allow changing gender after reveal). If no, create. Return the admin response.

    - `getAdminConfig(envelopeId: string)`: Returns `GenderRevealAdminResponse`. Get config, transform to admin response (includes genderValue, keys, validation state). Return null if not configured.

    - `resealReveal(envelopeId: string)`: Reset validation state (clear keyAValidated, keyBValidated, revealedAt). Preserve genderValue, keyA, keyB. Return success.
