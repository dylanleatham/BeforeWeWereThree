    5. **Create useGenderReveal hook** at `client/src/hooks/useGenderReveal.ts`:
    Follow the useWouldYouRather pattern for SignalR integration.

    State:
    - `phase: GenderRevealPhase` — starts as 'loading'
    - `gender: GenderValue | null` — only set when revealed
    - `keysValidated: number` — 0, 1, or 2
    - `keyLength: number` — from state endpoint (default 6)
    - `error: string | null` — validation error message
    - `isSubmitting: boolean` — while validate-key is in-flight

    On mount (useEffect):
    - Call getGenderRevealState(envelopeId)
    - If not configured: set phase to 'not-configured'
    - If revealed: set phase to 'keepsake', set gender
    - If keysValidated > 0: set phase to 'waiting' (assume this device's key was already entered on another session — the user can just wait or try their key)
    - Otherwise: set phase to 'key-entry'
    - Set keyLength from response

    SignalR events (useSignalREvent):
    - Listen for `genderRevealKeyValidated`: update keysValidated count, if phase is 'key-entry' or 'waiting', stay in current phase (the other device entered a key)
    - Listen for `genderRevealUnlocked`: set gender from event data, transition to 'ceremony' phase. This is the critical event — both devices get it simultaneously.

    Join SignalR group on mount: `activity:${envelopeId}` (same pattern as WYR/NameGame)

    Functions:
    - `submitKey(key: string)`: POST validateRevealKey. Handle response:
      - 'invalid_key': set error to REVEAL_KEY_INVALID string, clear input
      - 'key_already_used': set error to REVEAL_KEY_ALREADY_USED
      - 'waiting_for_partner': set phase to 'waiting', set keysValidated
      - 'revealed': set phase to 'ceremony', set gender (this user entered the second key)
      - 'already_revealed': set phase to 'keepsake', set gender

    - `onCeremonyComplete()`: Transition from 'ceremony' to 'keepsake' phase

    Return: { phase, gender, keysValidated, keyLength, error, isSubmitting, submitKey, onCeremonyComplete }
